# MVP 执行计划

## 1. 目标

在 12 周内完成 `Agent 指挥台` 的首版 MVP，打通从项目创建、Agent 接入、流程执行、审批追踪到证明书生成的完整闭环，并具备小范围真实用户内测能力。

## 2. 规划假设

- 团队规模：3-5 人核心研发团队
- 交付模式：双周一个迭代
- MVP 范围以文档包定义为准
- 主开发语言统一为 `TypeScript`
- `Python` 只作为辅助语言，承担离线任务、数据处理和专用 Worker
- 首版只维护 1 套核心控制平面，不做双后端并行架构

## 3. 里程碑总览

| 里程碑 | 周期 | 目标 |
| --- | --- | --- |
| P1 初步模型搭建 | 第 1-3 周 | 完成领域模型、工程骨架、基础数据链路和最小可运行框架 |
| P2 功能完善 | 第 4-8 周 | 完成核心业务能力与 MVP 闭环 |
| P3 UI 美化 | 第 9-10 周 | 完成 Web 和小程序关键页面的视觉优化与交互打磨 |
| P4 测试 | 第 11-12 周 | 完成联调、回归、修复和发布前验收 |

## 4. 分阶段计划

## 4.1 P1：完成初步模型搭建（第 1-3 周）

目标：

- 完成文档、信息架构和工程初始化
- 完成核心领域模型：`Workspace / Project / Agent / Task / Run / Artifact / Approval / Certificate`
- 完成 Monorepo 基础结构与共享类型包
- 完成本地 `SQLite + 文件产物存储 + 数据库轮询 worker` 开发环境搭建
- 跑通最小 API、Web、Worker 启动链路
- 固定 P1 Web 页面范围为 `/` 与 `/projects/[projectId]`

交付物：

- Monorepo 初始工程
- 数据库初版 schema 与 migration
- 核心模块脚手架
- 接口规范与领域对象定义
- P1 Web 页面地图与后续页面补齐边界

完成标准：

- 本地可启动 `web + api + worker`
- 核心对象模型和状态定义稳定
- 至少打通一个最小的 Task -> Run 数据链路

## 4.2 P2：功能完善（第 4-8 周）

目标：

- 完成全中文、双主题、低疲劳的 Web 控制台应用壳
- 完成 `工作台 / 项目 / 审批 / 执行代理 / 流程模板 / 证明书中心 / 接入配置` 一级页面
- 完成任务详情、执行记录详情、交付产物详情、项目设置、代理详情、模板详情等下钻页面
- 扩展 Dashboard、Approval、Agent、Workflow、Certificate、Integration Config 等共享类型与 API
- 形成一套可持续扩展的 P2 Web 控制台，而不是继续把信息堆在 P1 单页 cockpit 里

优先场景：

- 小程序项目交付流程

交付物：

- 可用的 Web 控制台核心业务模块
- 全中文明暗主题系统与左侧导航应用壳
- 项目、审批、代理、流程模板、证明书、接入配置等核心页面
- 覆盖扩展 API 的集成测试

P2 Web 页面补齐清单：

- `/projects` 项目列表页
- `/projects/[projectId]/tasks/[taskId]` 任务详情页
- `/runs/[runId]` Run 详情页
- `/approvals` 审批中心
- `/artifacts/[artifactId]` Artifact 详情页
- `/agents` Agent 列表页
- `/agents/[agentId]` Agent 详情页
- `/workflows` 工作流模板页
- `/workflows/[templateId]` 工作流模板详情页
- `/certificates` 证明书中心
- `/settings/integrations` 接入配置页

完成标准：

- Web 控制台主要页面都可独立访问和下钻
- 所有用户可见文案统一中文化，支持 `system / light / dark` 三态主题
- 从项目 cockpit 到任务、执行记录、审批、产物的主路径可稳定跑通
- P2 新增 API 具备基础集成测试覆盖
- 真实 OpenAPI Agent、小程序端、MCP Relay 继续后置到后续阶段

## 4.3 P3：UI 美化（第 9-10 周）

目标：

- 继续优化 Web 控制台和小程序的关键页面视觉层级
- 提升任务看板、Run 详情、审批页、证明书页的易读性
- 统一设计变量、间距、状态色和关键组件风格
- 修正 MVP 阶段影响观感和理解成本的交互问题

交付物：

- Web 控制台关键页面视觉优化版
- 小程序审批与项目详情界面优化版
- 基础 UI 规范和组件整理

完成标准：

- 核心路径界面可用于真实演示
- 主要页面在桌面和移动端都可稳定使用
- UI 不改变既定业务模型和接口协议

## 4.4 P4：测试（第 11-12 周）

目标：

- 完成联调、回归、异常场景验证和上线前修复
- 完成核心自动化测试和手工验收
- 进行试点项目演练和问题收口
- 输出发布建议和下一阶段迭代结论

交付物：

- 测试报告
- 缺陷清单与修复结果
- 发布前验收记录
- 试点验证总结

完成标准：

- 核心闭环端到端可稳定通过
- 高优先级缺陷已关闭或有明确处置结论
- 系统达到内测或试运行门槛

## 5. MVP Epic 拆分

| Epic | 负责人建议 | 依赖 | 结果定义 |
| --- | --- | --- | --- |
| E1 基础工程与身份体系 | 后端/全栈 | 无 | 工作区、成员、登录、权限骨架可用 |
| E2 项目与任务管理 | 产品 + 前后端 | E1 | 项目、任务、看板可用 |
| E3 Agent Registry | 后端 | E1 | Agent 注册、能力、状态可用 |
| E4 工作流模板与执行 | 后端 | E2/E3 | 模板可配置并触发 Run |
| E5 Run / Artifact / Approval | 后端 + 前端 | E2/E4 | 执行追踪和审批链路可用 |
| E6 小程序轻指挥端 | 前端 | E1/E5 | 可审批、可查看状态 |
| E7 过程证明书 | 后端 | E2/E5 | 可生成 PDF/JSON/验证信息 |
| E8 质量与运维 | QA/平台 | 全部 | 监控、测试、发布门禁到位 |

## 6. 双周迭代建议

## Sprint 1

- 完成仓库初始化、共享类型、鉴权、项目模型、Agent 模型

## Sprint 2

- 完成任务看板、Run 模型、OpenAPI Adapter、事件链路、最小 Worker 链路

## Sprint 3

- 完成模板执行、审批中心、证明书最小生成能力

## Sprint 4

- 完成小程序审批与状态视图、MCP Relay、模板扩展

## Sprint 5

- 完成 UI 美化、质量补强、内测问题修复、试点项目验证

## 7. 需求优先级规则

- Must：影响 MVP 闭环演示与核心价值验证，必须进入当前版本
- Should：提升体验和复用能力，可在 MVP 后半段进入
- Could：增强项，需在真实用户验证后再决定

## 8. Definition of Done

一个功能完成，必须同时满足：

- 需求说明和验收标准已明确
- 设计或接口文档已更新
- 代码合并并通过自动化检查
- 核心路径有测试覆盖
- 埋点、日志、错误码补齐
- 如涉及状态变更，已写入审计事件

## 9. 项目管理节奏

- 每日：异步站会，更新阻塞项和当日目标
- 每周：周会审视里程碑、风险和优先级
- 双周：迭代评审 + 回顾
- 每个里程碑结束：演示真实闭环，不接受只演示静态页面

## 10. 试点用户验证方案

- 目标数量：3-5 位首批试点用户
- 画像优先级：接单型开发者 > 小型工作室 > AI Native 团队
- 验证重点：
  - 是否愿意把真实项目放进系统
  - 是否愿意用小程序做审批
  - 是否认为过程证明书对客户交付有价值

## 11. 交付风险控制

- 对外接入先少后多，先打通一个再复制
- 小程序只做最必要控制面，避免拖累主线
- 证明书先做“可信展示”，不承诺法律效力
- 任何新增需求必须回答“是否增强交付闭环”

## 12. MVP 出口条件

满足以下条件后，可进入下一阶段商业验证：

- 有 3 个稳定模板场景
- 有 1 份客户愿意接收的过程证明书
- 有 3 个以上真实项目闭环记录
- 有可量化的用户反馈和复用数据
