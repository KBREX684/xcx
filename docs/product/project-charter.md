# 项目章程

## 1. 项目定义

- 项目名称：`Agent 指挥台`
- 内部英文名：`Agent Control Plane`
- 当前阶段：`MVP 定义与启动准备`
- 文档目的：明确项目目标、边界、角色、成功标准和治理方式

## 2. 项目愿景

为中国 OPC 与超轻团队打造一套真正可管理、可复用、可交付、可证明的 Agent Delivery OS，让用户不只是“使用 AI”，而是像管理真实团队一样管理 Agent，并能把 Agent 产能以可信方式交付给客户。

## 3. 项目使命

围绕 `管理 + 编排 + 证明` 三条主线，完成以下三件事：

1. 让用户在一个项目视角中看清多个 Agent 的任务、状态和贡献。
2. 让高频交付流程可以模板化、自动化、可审批、可追踪。
3. 让项目结果不仅有产物，还有可以给客户验收的过程证明。

## 4. 问题陈述

当前中国 OPC 的多 Agent 协作普遍存在以下问题：

- Agent 分散在不同产品和入口中，项目上下文不统一
- 任务、运行结果、审批记录和产物分散在聊天、代码库、文档和第三方平台
- 很难统一回答“谁在做什么、做到哪一步、出了什么问题”
- 缺少适合小团队的固定工作流模板和标准交付路径
- 移动端往往只有消息提醒，缺少真正的调度与审批能力
- AI 交付缺少过程透明度，客户对可信度和责任边界存疑

## 5. 项目目标

## 5.1 业务目标

- 在 3-6 个月内验证至少 10 个核心 OPC 用户对产品有持续使用意愿
- 验证“过程证明”能力能否提升客户验收通过率、签单率或复购意愿
- 形成 3 个以上可高频复用的交付模板场景

## 5.2 产品目标

- 支持多 Agent、多项目、多任务的统一管理
- 支持固定流程模板驱动的标准化交付
- 支持 Web 控制台和微信小程序双端协同
- 支持生成基础版项目过程证明书

## 5.3 研发目标

- 以单体优先、边界清晰的控制平面完成 MVP
- 以标准化对象模型统一 Agent、Task、Run、Artifact、Approval、Certificate
- 建立可观测、可审计、可扩展的接入与执行链路

## 6. 项目范围

## 6.1 MVP 必做范围

- 工作区、项目、任务、看板基础能力
- Agent 注册、能力描述、项目绑定、状态可视化
- 工作流模板、节点编排、手动触发、Webhook 触发
- 固定节点绑定固定 Agent
- OpenAPI 接入与基础 MCP 远程接入
- Run 状态追踪、审批、重试、催办
- 微信小程序审批与提醒
- 项目过程证明书基础版与验证链接

## 6.2 MVP 明确不做

- 通用型聊天产品
- 重型低代码搭建器
- 全行业企业级组织权限体系
- 完整财务计费系统
- 大范围第三方深度适配
- 法律意义上的产权证明系统
- 复杂 BI 分析系统

## 7. 核心用户

- 一人公司开发者
- AI Native 独立开发者
- 接单型工作室
- 2-10 人轻量产品团队
- 面向客户提供网站、小程序、自动化和 AI 解决方案的服务商

## 8. 典型场景

## 8.1 产品开发交付

需求整理、页面方案、编码实现、测试回归、上线说明和客户交付由多个 Agent 协作完成，平台沉淀任务链路与交付证明。

## 8.2 重复性业务流程

例如每周运营分析、项目访谈整理、交付前测试清单、阶段性周报，借助模板化工作流提高可复用性。

## 8.3 移动端指挥

用户通过微信小程序查看进度、审批关键节点、处理异常、重试失败任务并向客户展示项目状态。

## 9. 核心成功指标

## 9.1 北极星指标

- 每周活跃工作区中完成至少一次 `Task -> Run -> Artifact -> Approval -> Certificate` 闭环的比例

## 9.2 产品指标

- 每个工作区平均活跃 Agent 数
- 每周工作流触发次数
- 审批平均完成时长
- 证明书生成次数
- 可复用模板使用率

## 9.3 交付指标

- 首次交付闭环完成率
- 客户验收通过率
- 项目异常重试成功率
- 核心流程平均交付时长

## 10. 项目原则

- 以交付为中心，而不是以聊天为中心
- 以项目控制平面为中心，而不是以单个工具为中心
- 以标准对象模型为中心，而不是为每个接入单独做流程
- 以可验证过程为中心，而不是只看最终结果
- 以轻量可落地为中心，而不是一次做全

## 11. 关键角色与职责

| 角色 | 职责 |
| --- | --- |
| 项目发起人 | 明确方向、预算和商业化策略 |
| 产品负责人 | 用户访谈、需求定义、范围控制、优先级管理 |
| 架构师 | 技术选型、边界划分、关键决策、非功能目标把控 |
| 主工程师 | 核心模块实现、工程规范、代码质量与交付效率 |
| 前端负责人 | Web 控制台和小程序体验与交互落地 |
| 后端负责人 | 控制平面、工作流、接入层、证明链路实现 |
| QA/测试 | 测试策略、回归、验收标准、发布质量门禁 |
| 运维/平台 | 环境、监控、告警、备份、发布流程 |

## 12. 治理机制

- 周节奏：每周一次项目例会，确认进展、风险、范围变化
- 双周节奏：每两周一次里程碑评审，审视功能完成度和质量门禁
- 重大变更：涉及范围、架构或商业模式变化时，必须同步更新章程和 PRD
- 版本原则：MVP 只接受增强交付闭环价值的需求，不接受偏离定位的“顺手功能”

## 13. 里程碑

| 里程碑 | 时间窗口 | 结果定义 |
| --- | --- | --- |
| M0 项目启动 | 第 1 周 | 文档包、原型、技术路线、任务拆分完成 |
| M1 概念验证 | 第 4-6 周 | 打通一个 OpenAPI Agent 闭环并生成首份证明书 |
| M2 MVP 内测 | 第 10-12 周 | Web 控制台、小程序审批、3 个模板场景可用 |
| M3 商业验证 | 第 3-6 个月 | 10-30 位核心用户验证付费意愿与使用频率 |

## 14. 风险提醒

- 需求膨胀导致产品变重
- 适配过多生态导致研发分散
- 证明书能力如果不可信，会削弱核心差异化
- 小程序场景若定位不清，会变成缩水版 Web

## 15. 章程结论

本项目不是通用智能体平台，而是一套面向中国 OPC 场景、以项目交付和过程可信为核心的控制平面系统。所有后续产品和技术决策，均应优先服务这个定位。
